myallscripts — Logging & Output Conventions
=============================================
Reference this file when writing/updating any script under myallscripts,
so all scripts stay consistent and easy to read/grep.

1. Logger setup (put this near the top, after imports)
-------------------------------------------------------
logging.basicConfig(level=logging.INFO, format='%(asctime)s  %(levelname)-9s%(message)s', datefmt='%H:%M:%S')
log = logging.getLogger('<script-name>')   # e.g. 'kickmac-deploy, qwrap-traffic-config-dynamic-input.py'

- Always via the `log` object (log.info / log.warning / log.error / log.debug).
  Never use bare print() for actual log messages — print() is reserved ONLY
  for phase separators and final summary tables/banners (see sections 3 & 4).
- `--debug` CLI flag should call `log.setLevel(logging.DEBUG)`.
- Timestamps: %H:%M:%S (short, no date — these are short-lived interactive runs).

2. Per-host / per-action tags: [SCP] / [CLI] / [ROOT]
-------------------------------------------------------
When a log line represents a command/transfer being executed on a specific
AP, prefix it with the AP host, then the execution-path tag:

    log.info(f'[{host}] [SCP] {localPath} -> {remoteDst}')
    log.info(f'[{host}] [CLI] {cmd}')
    log.info(f'[{host}] [ROOT] {cmd}')

Tag meaning (pick based on how the command is ACTUALLY executed — verify,
don't assume):
  [SCP]  - file transfer (scp) to/from the AP.
  [CLI]  - command run inside the "config" user shell (su - config / cli -c "...").
            Used for all qwrap/wifiagent business commands.
  [ROOT] - command run in a root shell (ssh root@host, or su - after root login).
            Used for filesystem-level ops (mkdir, chmod, nohup launch, etc).

Do NOT mix tags — if a script only ever uses one execution path, it can skip
tagging non-ambiguous internal steps, but any AP-targeted command should still
show [host] for readability in concurrent (multi-AP) runs.

3. Phase separators (linear / single-threaded scripts only)
-------------------------------------------------------
For scripts that run through distinct sequential phases (parse args -> resolve
targets -> build config -> push), wrap each phase's start with a plain-text
banner using print() (not log), so it doesn't get a timestamp/level prefix:

    print('-' * 40)
    print('Resolve target AP(s)')
    print('-' * 40)
    apIps = resolveApList(args)

    print('\n' + '-' * 40)
    print('kickmac options')
    print('-' * 40)
    kickmacArgsLine = promptForKickmacArgsLine()

Rules:
  - Use print(), never log.info(), for the separator lines themselves.
  - Keep the header short (3-5 words, Title Case first word only).
  - Put the separator BEFORE any code/log lines belonging to that phase —
    including the very first log.info() of that phase. Double check nothing
    that logically belongs to phase N is left above phase N's separator.
  - Except for the very first separator in the script, prefix every phase
    separator with a blank line (`print('\n' + '-' * 40)`), so each phase
    reads as its own visually distinct block instead of running together.
    The first separator doesn't need it (nothing above it yet).
  - Do NOT add separators to scripts that run AP actions CONCURRENTLY across
    multiple hosts (e.g. qwrap-manager.py). Concurrent runs interleave
    log lines from different hosts in real time, so a banner would falsely
    imply a phase boundary that doesn't exist for all hosts at once. Rely on
    the [host] tag instead — it's grep/filter-safe regardless of interleaving.
  - Good candidates: one-shot deploy/config scripts where phases genuinely
    run to completion in order before the next starts (kickmac-deploy.py,
    qwrap-traffic-config.py, qwrap-traffic-config-dynamic-input.py,
    qwrap-traffic-75-25.py).

4. Final summary (end of run)
-------------------------------------------------------
If a script processes multiple APs, always end with a final summary —
prefer TABLE format whenever the result has 2+ uniform columns across all
APs (e.g. AP IP + one or more status columns). Only fall back to plain
LINE format when a table doesn't fit (single value per AP, or highly
variable/free-text results that would break column alignment).

Table format (preferred, when applicable) — fixed-width columns, header,
top/bottom rules made of '=' (visually distinguishes the final summary from
the '-' phase separators used during the run), and a leading blank line so
it stands apart as its own block:

    W = 20
    numCols = 3
    ruleWidth = W * numCols + (numCols - 1) * 2   # fixed-width cols + 2-space gaps
    print("\n" + "=" * ruleWidth)
    print(f"{'AP IP':<{W}}  {'FileOp':<{W}}  {'Client':<{W}}")
    print("=" * ruleWidth)
    for r in sorted(summary, key=lambda x: x["ap"]):
        print(f"{r['ap']:<{W}}  {r.get('fileop', '-'):<{W}}  {r.get('client', '-'):<{W}}")
    print("=" * ruleWidth + "\n")

    # Example output:
    # ================================================================
    # AP IP                 FileOp                Client
    # ================================================================
    # 10.86.204.227         ok (252 sessions)     ok (280 sessions)
    # ================================================================

  - Add columns as needed (radio breakdown, error reason, PID, etc.) — keep
    each column fixed-width (`W`), INCLUDING the last column, so rows stay
    aligned regardless of value length variance; truncate or widen `W` if a
    value is expected to overflow.
  - The '=' rule length MUST match the row width exactly: for N columns it's
    `N * W + (N - 1) * 2` (2-space gaps between columns). Don't hardcode this
    — compute it from the actual column count, or the bars will be shorter
    than the rows and the table will look broken/misaligned.
  - Sort rows (usually by AP IP) so output is stable across runs.

Line format (fallback, when a table doesn't make sense) — one line per AP,
same style as section 5:

    log.info("%s: configure succeeded", ip)
    log.error("%s: configure failed — %s", ip, err)

  - Use this when there's only one result value per AP (no extra columns to
    justify a table), or when messages are free-text/variable-length and
    would break table alignment.

5. Per-AP status/result lines
-------------------------------------------------------
Use a consistent, single-line, greppable format per AP, e.g.:

    log.info("%s: configure succeeded", ip)
    log.error("%s: configure failed — %s", ip, err)

Prefer %s-style lazy formatting in log.info/error/debug calls (not f-strings)
for these — it's the existing convention across scripts and avoids doing
string work when the log level is filtered out.

6. Concise per-AP breakdown lines (band/radio config, counts, etc.)
-------------------------------------------------------
When summarizing multi-value config per AP (radios, bands, counts), use a
single compact line per AP instead of one line per value:

    log.info("[%s] %s via %s", ip, radioBreakdown, ap_url[ip])
    # -> [10.86.204.227] 2.4G=28v/28f/28c/IPv4/hostname, 5G=28v/28f/28c/... via http://...

7. Per-AP log colorization (optional, for concurrent multi-AP scripts)
-------------------------------------------------------
When a script pushes to multiple APs CONCURRENTLY colorize each AP's lines by
a color assigned to that specific host, so you can visually track one AP's
output as it threads through the interleaved stream. Implemented once in
qwrap-traffic-75-25.py — copy this pattern (not a shared import, see Do NOT).

a) Global toggle (next to other global booleans like SEND_HEARTBEAT):

    # 1 -> colorize log output (still auto-disabled when stdout isn't a TTY,
    #      e.g. piped to a file, or when NO_COLOR env var is set)
    # 0 -> never colorize, even on a terminal (plain text always)
    COLOR_LOGS = 1

b) Palette + assignment (near the logging.basicConfig setup): a fixed list
   of ANSI 256-color codes chosen to stay readable on a DARK terminal
   background (bright/saturated hues — blues, oranges, greens, pinks,
   cyans, etc. — avoid dark/dim colors that wash out). Size the palette to
   comfortably cover the max number of hosts you expect (20 was enough for
   qwrap-traffic-75-25.py); colors cycle via modulo past that.

   Assign colors by iterating the host/AP config dict's key order (NOT by
   IP/subnet) — this is what makes mixed subnets (10.85.x, 10.86.x,
   10.87.x, etc., in any proportion) each still get one distinct color as
   long as total hosts <= palette size:

    _LOG_COLOR_ENABLED = COLOR_LOGS and sys.stdout.isatty() and os.environ.get("NO_COLOR") is None

    _AP_COLOR_PALETTE = [
    "\033[38;5;208m",  # orange
    "\033[38;5;34m",   # green
    "\033[38;5;226m",  # yellow
    "\033[38;5;27m",   # blue
    "\033[38;5;201m",  # magenta
    "\033[38;5;51m",   # cyan
    "\033[38;5;118m",  # lime
    "\033[38;5;218m",  # pink
    "\033[38;5;130m",  # brown
    "\033[38;5;100m",  # olive
    "\033[38;5;215m",  # apricot
    "\033[38;5;25m",   # navy
    "\033[38;5;54m",   # indigo
    "\033[38;5;178m",  # gold
    "\033[38;5;39m",   # sky blue
    "\033[38;5;80m",   # turquoise
    "\033[38;5;93m",   # purple
    "\033[38;5;30m",   # teal
    "\033[38;5;183m",  # lavender
    "\033[38;5;121m",  # mint
        # ... extend to cover expected max host count
    ]
        # ... extend to cover expected max host count
    ]
    _LOG_RESET = "\033[0m"

    _AP_LOG_COLORS = {
        ip: _AP_COLOR_PALETTE[i % len(_AP_COLOR_PALETTE)]
        for i, ip in enumerate(AP_CONFIG)   # insertion order of the config dict
    }

c) Formatter: wrap the WHOLE log line in the color for whichever host IP
   appears in that line's "[ip]" bracket prefix (per section 2's tagging
   convention). Lines with no bracketed IP (global/setup lines — discovery,
   endpoint pool sizes, "Targeting N AP(s)", etc.) are left uncolored, not
   guessed at:

    _IP_BRACKET_RE = re.compile(r"\[(\d{1,3}(?:\.\d{1,3}){3})\]")

    class _PerApColorFormatter(logging.Formatter):
        def format(self, record):
            line = super().format(record)
            if not _LOG_COLOR_ENABLED:
                return line
            match = _IP_BRACKET_RE.search(record.getMessage())
            color = _AP_LOG_COLORS.get(match.group(1)) if match else None
            return f"{color}{line}{_LOG_RESET}" if color else line

    _log_handler = logging.StreamHandler()
    _log_handler.setFormatter(_PerApColorFormatter(
        fmt='%(asctime)s  %(levelname)-9s%(message)s', datefmt='%H:%M:%S'))
    logging.basicConfig(level=logging.INFO, handlers=[_log_handler])
    log = logging.getLogger('<script-name>')

Rules:
  - A given host/AP must ALWAYS get the same color across runs regardless of
    which subset is targeted (e.g. via an --ap filter) — color comes from
    its position in the config dict, not from the filtered/resolved subset.
  - Only color lines that already follow section 2's "[host] ..." tagging
    convention — don't invent a separate tagging scheme just for color.
  - Must auto-disable (plain text, no escape codes) when stdout isn't a TTY
    or when NO_COLOR is set, so redirected/piped output and log files never
    contain raw ANSI escape codes.
  - Keep this an explicit opt-out via COLOR_LOGS (default 1), consistent
    with how other global behavior toggles in the script work.

8. Do NOT
-------------------------------------------------------
  - Don't change the base logging.basicConfig format (timestamp/level style)
    per-script — keep it identical everywhere.
  - Don't extract these helpers into a shared common module — every script
    stays self-contained/standalone. Copy the pattern, not a shared import.
  - Don't add phase separators to loop-based/continuous scripts (monitors)
    or to concurrent multi-AP scripts (see section 3).
  - Don't use print() for anything that should be filterable/greppable by
    level or host — that always goes through log.
  - Don't hardcode colors by subnet/IP pattern — always assign by config
    dict iteration order so mixed subnets still each get a distinct color.
